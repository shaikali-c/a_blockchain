# Database

Axis uses LevelDB for persistence.

This document explains what is stored, how keys and values are shaped, and how consistency works.

## 1. Why a database is needed

Without persistence, the node would lose all blocks and pending transactions when the process exits.

Axis uses the database to preserve:

- blockchain history,
- mempool contents.

## 2. Database abstraction

The persistence wrapper is:

- `DatabaseManager`

Declared in `axis/include/axis/storage/database_manager.h` and defined in `axis/src/storage/database_manager.cpp`.

It is intentionally small.

## 3. Database instances in Axis

The `Blockchain` object owns two databases:

- `blocksDB("blocks")`
- `poolsDB("pool")`

These paths are relative to the working directory.

### Implication

Run the executable from the repository root unless you intentionally want the databases created elsewhere.

## 4. What is stored in `blocks/`

The `blocks/` LevelDB stores serialized blocks.

### Key format

Generated by `Blockchain::generateBlockKey()`.

It creates a zero-padded decimal string using width 10.

Examples:

```text
0000000001
0000000002
0000000003
```

### Why this format was chosen

Because lexicographic ordering of fixed-width numeric strings matches numeric order.

That means iterating the LevelDB keys from first to last also yields block order.

### Value format

The value is `Block::serialize()` output.

## 5. What is stored in `pool/`

The `pool/` LevelDB stores pending mempool transactions.

### Key format

Transaction hash encoded as hex string:

```text
<64 hex chars>
```

### Value format

Serialized transaction bytes from `Transaction::serializeTransaction()`.

## 6. Startup recovery process

## Loading blocks

`Blockchain::loadBlocks()`:

1. iterates all block records in `blocksDB`,
2. deserializes each block,
3. adds every block transaction to the `transactions` map,
4. applies `updateUTXO()` to rebuild current spendable state,
5. appends the block to `blocks`,
6. records hash-to-index mapping in `blocksMap`.

### Why replay is used

Because the block database is treated as the source of truth for confirmed chain history.

## Loading the mempool

`Blockchain::loadPoolTransactions()`:

1. iterates all records in `poolsDB`,
2. deserializes each transaction,
3. adds it to `transactionsPool`,
4. marks its inputs in `mempoolInputs`.

### Why `mempoolInputs` is rebuilt

So the node can continue preventing pending double-spends after restart.

## 7. Consistency model

Axis uses simple write-through behavior.

### For accepted mempool transactions

When a transaction is accepted:

1. insert into `transactionsPool`,
2. reserve inputs in `mempoolInputs`,
3. save to `poolsDB`.

### For genesis block

When created:

1. build block,
2. push it into `blocks`,
3. save it to `blocksDB`,
4. update the UTXO set.

## 8. Error handling

`DatabaseManager` throws `std::runtime_error` when:

- DB open fails,
- read fails for reasons other than not-found,
- write fails,
- delete fails.

### Special case: missing key reads

`loadKey()` returns an empty string for not-found instead of throwing.

This mirrors LevelDB’s not-found behavior being non-fatal in many workflows.

## 9. What is not stored directly

The active UTXO set is not persisted in its own database.

Instead, it is rebuilt by replaying block transactions.

### Benefit

Simple consistency story.

### Cost

Longer startup time as chain size grows.

## 10. Key/value examples


## Mempool record example



## 11. Design tradeoffs

### Advantages

- very simple persistence layer,
- ordered block iteration is easy,
- transaction recovery is straightforward,
- LevelDB is lightweight and embeddable.

### Disadvantages

- no atomic multi-record transactions across different logical structures,
- no dedicated UTXO index on disk,
- no schema/versioning metadata,
- mempool and chain consistency during crashes is only as strong as operation ordering.

## 12. Future improvements

Potential next steps:

1. persist UTXO state explicitly,
2. remove mined transactions from pool DB when block acceptance exists,
3. add batch writes for logically related updates,
4. add metadata keys for chain tip and format version,
5. add recovery checks for partially applied state changes.

## 13. Summary

Axis uses LevelDB as a simple binary blob store:

- blocks are stored in ordered numeric-string keys,
- mempool transactions are stored by transaction-hash key,
- confirmed spendable state is rebuilt from blocks,
- pending-input reservations are rebuilt from the mempool database.
